## Concurrent two-context assessment

A later read-only assessment considered starting a second complete Chromium campaign while the frozen one-context reference remained active. This is not yet recommended as a safe concurrent experiment. No second campaign was launched by this audit.

The supported override is `npm run test:formatting -- --browser chromium --contexts 2 --out build/formatting-oracles/final-current-chromium-contexts-2`, optionally prefixed with `ORACLE_GAPS_PROFILE=1`. The wrapper appends user arguments after its default `--contexts 1`; `parseArgs` assigns each occurrence to the same option, so the final `--contexts 2` wins. With no `--oracle`, `--sample` or `--only`, the complete sources, receiver flag, histories, seeds, time limits and mutant set remain. A distinct output directory is mandatory. This command is documented here and has not been executed by the reviewer.

Most inspected isolation is suitable: each wrapper creates its own BrowserServer, random-port disposable Miniflare application, database/bucket bindings and temporary application bundle; the CLI uses a PID-namespaced harness and separately claimed output directory. Its cleanup treats a live PID or EPERM as alive, preserving another active run. Each warm CLI context has its own Vite patch state and one worker; transformed-module disk caching is disabled. Receiving histories use separate BrowserContexts, per-history IPs and separately created item IDs. Picker/settings/search provider interception is attached to the individual context; restore/save routes use the individual item endpoint. Chromium's native-history helper does not invoke the macOS WebKit native-window workaround.

One important resource is not covered by that isolation: completed-link workflows deliberately use the actual native clipboard through `navigator.clipboard.writeText/readText` and native `ControlOrMeta+v`. Stable arranged clipboard delivery is itself asserted. BrowserContext storage, permission and route isolation do not establish isolation of native clipboard contents. Two contexts within the proposed second campaign share a BrowserServer, and separate concurrent Chromium campaigns may share the host clipboard. The source inspection does not establish either isolation guarantee. A clipboard write racing another history's read/paste could produce a setup/premise failure, nondeterminism or misleading mutant evidence, and could affect later clipboard-owning runs in the main reference. This concern must be cleared before treating the proposed concurrent full run as safe. The existing wrapper requests one context for default/workflows; this review does not claim the undocumented reason for that choice.

A point-in-time local resource snapshot around 02:33 PST reported 18 available CPUs, 64 GiB RAM, load averages approximately 3.8/3.4/3.3 and `memory_pressure -Q` reporting 80% free. Available capacity alone does not clear clipboard interference or guarantee unchanged seven-second host/60-second test timing under additional browser load. Neither a local concurrent speedup nor GitHub Linux performance is established.

The recommended next step is to establish native clipboard isolation or a genuine host-level exclusion boundary before running complete two-context campaigns, then compare complete baseline hashes, nondeterminism, mutant identities/classifications and law verdicts. Such a boundary would itself require a reviewed change or isolated host experiment; no weakened budgets, family sharding or removed clipboard histories are proposed. The main campaign must continue unchanged. All 402 frozen runtime hashes remained unchanged through this documentation-only assessment.

## Further read-only fallback assessment

Mutation-ID partitioning across isolated CI hosts differs from selecting oracle families, but the pin supplies no `--shard` or `--list-mutants` option. Its `--only` filter also narrows both baselines to the selected mutations' owner-file union (`check.mjs` around2081–2111), even when the wrapper discovers all fourteen oracle files. Unknown selectors can be silently unmatched. Internal `analyze`, `assignKeys` and `loadAuthored` functions are not a supported public enumeration interface. A future partitioner would need pin/hash guards, a complete mutation universe, explicit per-shard baseline coverage, frozen input identities and an aggregator rejecting missing/extra/duplicate/unmatched IDs, incomplete reports, baseline failures and nondeterminism. Every constituent report would remain partial; equivalence to the unfiltered reference is unproved.

Config-only helper-first execution is also unavailable. The pin forces `KeepOrder` (`check.mjs` around771), lexically sorts baseline paths (around2102–2108), and re-sorts baseline units by filepath (`classify.mjs` around219–223). `targetsOf` derives reaching-owner priority from that normalized order (around274–283). Custom Vitest sequencing therefore cannot move a cheap distinguishing list owner ahead of a longer interaction owner. Renaming files would change report identities and ambient seeds, so it is not a frozen-input workaround.

A future runner scheduling control could try cheaper reaching owners while retaining canonical baseline/report order, file identities, seeds, budgets and registered-law judgment. Adoption would require unchanged baseline observations, exact complete mutation coverage, reproducible law kills and review of every classification difference. Such an optimization would not remove the observed unmutated validation cost. These assessments launched no campaign and changed no runtime or test input.
