## Supported findings

### Isolation mode is absent from CLI report/cache identity

**Claim challenged:** an ordinary CLI report identity can distinguish shared and process host topology, or daemon evidence can safely cross those modes.

**Authority/source:** ORC-005/010/012 and the pinned runner's documented evidence contract. The wrapper removes `--browser-isolation` from forwarded arguments and supplies `FORMATTING_ORACLE_BROWSER_ISOLATION` in the environment. `identityOf` hashes files and CLI options, not this environment value. The unit cache global key likewise excludes arbitrary environment values; `check.mjs` explicitly documents that limit. The existing wrapper still forwards `--daemon`.

**Smallest consequence:** run the same after-sources/options once in shared mode and once in process mode. The meaningful host topology changes, but its mode is absent from the CLI identity. A daemon first created under one disposable application/topology can retain environment/host state and reuse evidence without this boundary appearing in its key. This external-input limitation predates the proposal; the new opt-in mode makes it necessary to address explicitly.

**Evidence status:** read from source; VM parsing confirmed that the new wrapper consumes the mode before invoking the CLI. No daemon was started and no cache reproduction was attempted.

**Repair/gate:** the disposable integration command must be cold and record isolation mode, platform/architecture, actual browser version/binary/executable override, wrapper/input hashes and context count in an explicit host receipt. Do not use equality of CLI run IDs to claim equality of topology. Before routine adoption, reject daemon mode for this wrapper, or implement a reviewed external-host identity/invalidation contract. A documented cold-only parent command and separate manifest are sufficient for the bounded experiment; they are not a general cache fix.

### The proposal overstates default file isolation

**Claim challenged:** the runtime relies on Vitest's default test-file isolation being enabled.

**Authority/source:** ownership and failure fidelity (ORC-005/010). `check.mjs` `warmContext` explicitly sets `isolate: false` and one worker per warm CLI context. In a batch, `capture-setup.mjs` resets module state with `vi.resetModules()` for each non-skipped `run.units` copy. Canonical skip handling can avoid resetting an already killed copy, whose tests then run nothing.

**Consequence:** per-unit private Browser ownership depends on the pin's module reset and sequential unit completion, not the project's default isolation setting. Keeping the pin/loader invariant is necessary; a future runner change could accidentally reuse a module-local closed Browser or share a live one.

**Evidence status:** read from source. The candidate's module-local `connection`/`ownedBrowser` are fresh on actual re-evaluation. No multi-unit browser execution was run by this reviewer.

**Repair/gate:** correct the proposal's isolation sentence. In the disposable integration, prove two or more non-skipped units receive distinct owned processes and that the previous process has ended before its worker advances. Include normal units, selected suffix copies, authored units, a skipped copy after a real kill, and a context replacement. No file renaming or test filtering is needed.

### Setup validation prose should distinguish missing from malformed inputs

The code rejects missing origin/cookie/required shared endpoint before acquisition. It does not parse and validate every malformed URL/cookie before acquisition; those can fail during `addCookies`, routing or navigation and then use the acquired-browser cleanup path. The implementation covers that path. Correct the proposal table's broad “bad origin/cookie” preflight claim and include malformed inputs in the post-acquisition failure experiment. This is a documentation precision issue, not a demonstrated leak.

## Acquisition, cleanup and option routing

The candidate keeps one lazy connection promise per evaluated driver module. Concurrent callers share that promise; a failed setup remains a rejection rather than silently retrying inside another history. A successful unit obtains either an owned direct-launched Browser or a connected Browser client. The handle is assigned to `ownedBrowser` immediately after acquisition, before context/page/cookie/route/navigation setup. All later setup failures attempt closure. If that closure fails, `AggregateError([original, cleanup], …, {cause: original})` preserves both identities. `afterAll` suppresses only a duplicate rejected setup promise; the original caller still receives the setup rejection. Successful setup reaches `afterAll`, which awaits closure once. A normal close failure remains a hook/harness diagnostic.

`closeOwnedBrowser` clears ownership before awaiting close. That prevents accidental repeated close attempts but is not evidence that a failed close released the process. The successful connection promise still contains the Browser reference; no explicit retry/supervisor path is implemented. Timeout, cancellation and worker termination can bypass `afterAll`, and the parent wrapper has no private BrowserServer handle in process mode. These are mandatory real lifecycle gates, not claims already established by the source or mocks.

The Browser/BrowserServer distinction is appropriate. A successful direct `launch` returns a Browser whose close owns the local process. A connected Browser's close owns the client connection/its contexts while the wrapper retains the shared BrowserServer. The public API shape is compatible with existing `applicationDriver`, `sessionDriver` and `mixedDriver` callers, which obtain a Browser and create/close their own history contexts. No driver now closes the entire process per history. Existing Chromium histories remain sequential inside each file/unit; the proposal does not support adding concurrent tests or simultaneously running clipboard histories within that unit.

The wrapper validates the mode against the selected engine before `formattingApplication()` is called. CLI mode overrides the environment; missing/invalid values fail rather than degrading to shared. Process mode is restricted to Linux Chromium. The wrapper sets an empty endpoint in process mode, preventing an inherited shared endpoint from being selected. Both parent `launchServer` and private `launch` receive the same helper-generated `headless: true` plus optional `FORMATTING_ORACLE_BROWSER_EXECUTABLE`. The existing environment spread retains the executable override and Playwright browser path. No profile, clipboard replacement, source normalization, seed, budget or selection change is present in the diff.
